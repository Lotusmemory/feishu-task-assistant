# 飞书聊天总结双方案实施计划

日期：2026-07-15
适用项目：飞书客服与任务助理

## 0. 最终建议

第一版最合理的实施路径是：

```text
统一飞书机器人入口
+ 统一时间范围解析
+ 可替换的消息读取适配器
+ 共用的摘要与任务草稿模块
+ 用户主动发起的单次读取控制
+ 摘要结果只返回请求者本人
```

先用方案 A「单用户本地 `lark-cli` 桥接」完成 1～2 周内部试点，验证用户是否持续使用、摘要是否真正节省时间；达到试点门槛后，再实施方案 B「公司统一机器人 + 多用户独立 OAuth」。

方案 A 不应做成一次性代码。第一版就应把消息读取定义为统一接口，使时间解析、分页结果标准化、摘要、任务草稿和回复逻辑能够原样复用于方案 B。

第一版暂不建议做：

- 不为每名员工部署独立机器人或独立服务。
- 不使用一个公共员工账号替多人读取聊天。
- 不解析图片、语音、视频、文件和卡片。
- 不自动读取聊天，也不建立后台定时监控。
- 不自动创建任务；任务草稿仍需本人确认。
- 不建设管理后台、计费系统或复杂租户体系。

推荐 MVP 场景是：用户私聊机器人发送“总结 2026-07-01 到 2026-07-15 的聊天”，系统读取该用户有权访问的文本消息，生成重要事项、决策、待办、风险和相关人员摘要。这个场景输入明确、结果可人工核对、风险边界清晰，也能直接测量节省的整理时间。

总体成功标准：试点请求成功率不低于 90%，摘要事实准确率不低于 95%，摘要平均可在 60 秒内返回，原始聊天正文不落盘、不进入 Base、不发送给其他人员。

## 1. 背景与目标

当前项目已经具备以下能力：

- 识别明确起止日期的聊天总结请求。
- 以用户身份搜索消息、处理分页并分批读取正文。
- 只保留可总结的文本消息，并按时间排序。
- 调用 MiniMax 输出固定结构摘要和任务草稿。
- 对用户令牌加密存储，并支持 OAuth 刷新。
- 将结果只回复给请求者本人。

当前待决策的不是“能不能总结”，而是“用户身份如何安全地提供给消息读取层”。

本计划的目标是提供两套完整实施路径：

1. 方案 A：单用户本地 `lark-cli` 桥接，去掉公网 HTTPS OAuth 回调依赖，用最低成本验证价值。
2. 方案 B：公司统一机器人、多用户独立 OAuth，满足正式推广所需的权限隔离、审计、稳定性与运维要求。

## 2. 共用产品范围

### 2.1 用户入口

第一版仅支持用户主动发送带两个明确日期的请求，例如：

```text
总结 2026-07-01 到 2026-07-15 的聊天
汇总 2026年7月1日 到 2026年7月15日 的消息
```

系统按 `Asia/Shanghai` 时区将开始日期解释为 `00:00:00`，将结束日期解释为 `23:59:59`，起止日期均包含在范围内。

### 2.2 输出范围

输出固定包含：

- 重要事项 `important`
- 已确认决策 `decisions`
- 待办 `todos`
- 风险、建议和未确认假设 `risks`
- 相关人员 `people`
- 可选任务草稿 `taskDrafts`

第一版只处理文本消息。任务草稿必须由请求者再次确认后才能写入 Base。

### 2.3 隐私边界

- 用户主动发送带时间范围的总结请求，视为本次单次读取授权。
- 只读取当前调用身份原本可访问的消息。
- 不把原始聊天正文写入文件、日志、Base 或任务记录。
- 摘要不发送给 Leader、群聊成员或管理员。
- 日志只记录请求 ID、请求者、起止时间、消息数量、耗时、结果状态和错误类型。
- 日志不得包含 access token、refresh token、OAuth code、消息正文或完整授权 URL。

## 3. 共用总体架构

```text
飞书用户
  │ 私聊总结请求
  ▼
飞书机器人事件入口
  │
  ├─ 时间范围解析与校验
  │
  ├─ ChatHistoryProvider（可替换）
  │    ├─ 方案 A：LarkCliChatHistoryProvider
  │    └─ 方案 B：OAuthChatHistoryProvider
  │
  ├─ 消息标准化、去重、排序、分页完整性检查
  │
  ├─ ChatSummary（MiniMax）
  │
  ├─ 可选任务草稿确认
  │
  ▼
仅回复请求者本人
```

统一读取接口建议保持为：

```js
listTextMessages(actorOpenId, {
  startIso,
  endIso,
}) => {
  messages: [{ messageId, chatId, createTime, senderId, text }],
  incomplete: boolean,
}
```

方案 A 和方案 B 都必须遵守该返回结构。摘要层不得知道消息来自 CLI 还是 OAuth。

## 4. 方案 A：单用户本地 `lark-cli` 桥接

### 4.1 适用范围

适用于一名内部负责人或极小范围试点，由一台固定 Mac 持续运行服务。所有总结请求都必须来自预先配置的唯一飞书 `open_id`。

该方案的目标是验证业务价值，不是满足公司多人生产使用。

### 4.2 方案架构

```text
唯一试点用户
  │
  ▼
统一飞书机器人
  │ 校验 sender.open_id == ALLOWED_CHAT_SUMMARY_OPEN_ID
  ▼
本地 Node 服务
  │ 以受限参数调用 lark-cli
  ▼
lark-cli 当前用户登录态
  │
  ▼
飞书消息搜索与读取 API
```

Codex只用于开发、诊断和维护，不作为运行时桥接组件。关闭 Codex 后，本地 Node 服务仍应独立工作。

### 4.3 明确实施内容

| 模块 | 实施内容 | 交付物 |
| --- | --- | --- |
| 配置 | 新增读取模式和唯一允许用户配置 | `CHAT_HISTORY_PROVIDER=lark-cli`、`ALLOWED_CHAT_SUMMARY_OPEN_ID` |
| CLI 预检 | 启动时检查 `lark-cli` 是否存在、当前身份是否为 user、授权是否有效 | 启动检查和安全错误信息 |
| CLI 读取适配器 | 使用参数数组调用 `lark-cli im +messages-search`，传入起止时间、`--page-all`、`--as user` 和 JSON 输出 | `LarkCliChatHistoryProvider` |
| 结果转换 | 将 CLI JSON 转换成统一消息结构，过滤非文本、去重并排序 | 标准化转换函数 |
| 身份门禁 | 非允许用户发起请求时不调用 CLI，直接返回“不支持当前用户” | 请求者校验 |
| 错误处理 | 区分未登录、授权过期、缺少 scope、CLI 不存在、读取超时、输出格式异常 | 可操作的中文提示和结构化日志 |
| 进程控制 | 限制最大执行时间和最大输出，禁止 shell 字符串拼接 | 安全子进程封装 |
| 原有 OAuth | CLI 模式下不启动 OAuth server、不要求 Token Vault 和回调配置 | 条件化组装逻辑 |
| 文档 | 补充首次授权、启动、退出登录、故障恢复和隐私说明 | README 运维章节 |

### 4.4 实施步骤

#### A1. 固化成功标准和安全边界

1. 确认唯一试点人的飞书 `open_id`。
2. 确认只处理该用户主动发起的私聊请求。
3. 确认第一版只读取文本消息。
4. 确认摘要结果不自动转发、不自动创建任务。

验证：形成配置清单；缺少允许用户时服务拒绝以 CLI 模式启动。

#### A2. 抽象消息读取接口

1. 保留现有 `createChatHistory` 作为 OAuth Provider。
2. 新增 `createLarkCliChatHistory`，实现相同的 `listTextMessages` 接口。
3. 让 `createChatSummaryRequest` 只依赖统一接口。
4. 使用配置决定注入哪个 Provider。

验证：同一组契约测试分别运行在两个 Provider 上，返回字段和排序行为一致。

#### A3. 实现安全 CLI 调用

1. 使用 Node `execFile` 或 `spawn` 参数数组，不使用 `exec` 和 shell 拼接。
2. 只允许程序生成固定命令和固定参数，不接受用户原始字符串作为 CLI 参数。
3. 设置执行超时、最大输出和并发上限。
4. 关闭更新提示，确保 JSON 输出稳定。
5. 解析退出码与结构化错误，不回显令牌或底层敏感信息。

验证：包含引号、反引号、`$()` 和换行的用户输入不能改变实际命令；超时后子进程被终止并返回安全提示。

#### A4. 增加唯一用户门禁

1. 在调用 CLI 前比较事件发送者 `open_id` 与允许用户配置。
2. 群聊请求即使 `@机器人` 也不允许触发私人聊天总结。
3. 非允许用户请求不得产生飞书消息搜索调用。

验证：允许用户成功；其他用户和群聊请求的 CLI 调用次数均为 0。

#### A5. 本机授权与运行配置

1. 安装并配置 `lark-cli`。
2. 使用用户身份执行设备码授权。
3. 检查 `whoami` 与授权状态。
4. 在 `.env` 配置 CLI 模式和允许用户。
5. 启动 Node 服务并完成真实消息读取测试。

验证：无需公网 HTTPS 回调；重启 Node 服务后仍能使用现有 CLI 登录态读取消息。

#### A6. 端到端试点

1. 准备一个只包含已知测试消息的飞书会话和时间范围。
2. 发送总结请求。
3. 人工对照原消息核验摘要。
4. 模拟 CLI 未登录、授权过期、网络失败和超长范围。
5. 连续试用 1～2 周，记录使用次数、成功率、平均耗时和人工修改量。

验证：满足方案 A 验收表后才进入方案 B。

### 4.5 方案 A 验收标准

| 类别 | 验收项 | 明确标准 |
| --- | --- | --- |
| 功能 | 时间范围解析 | 支持两种约定日期格式；无效日期和起止颠倒 100% 被拒绝 |
| 功能 | 真实消息读取 | 能读取允许用户在指定闭区间内可访问的全部文本消息，并按时间排序 |
| 权限 | 唯一用户隔离 | 非配置用户、群聊请求触发消息读取的次数为 0 |
| 权限 | 最小权限 | CLI 使用 user 身份；不使用公共员工账号给多人提供服务 |
| 安全 | 命令注入 | 用户输入不能成为 shell 语法；自动化恶意输入测试全部通过 |
| 隐私 | 原文处理 | 原始正文不出现在文件、Base、普通日志和他人消息中 |
| 稳定性 | 请求成功率 | 在授权和网络正常时，试点请求成功率不低于 90% |
| 性能 | 返回时间 | 95% 的 7 天范围请求在 60 秒内返回或给出明确进度/失败提示 |
| 质量 | 事实准确率 | 抽查摘要中的事实性陈述，正确率不低于 95% |
| 质量 | 可用率 | 至少 70% 的试点摘要无需重做，只需轻微编辑即可使用 |
| 运维 | 故障可恢复 | CLI 未登录、授权过期和进程超时都有明确恢复步骤，不需修改代码 |
| 回归 | 自动化测试 | 全量 `npm test` 通过，CLI Provider 新增契约、门禁、超时和错误测试 |

### 4.6 方案 A 停止条件

出现任一情况，应停止扩大试点并先修正：

- 非允许用户能够触发读取。
- 原始消息出现在持久化日志或 Base。
- 摘要将未确认建议稳定误判为已确认决策。
- 一周内请求成功率低于 80%。
- 用户每周主动使用少于 3 次，且不能证明节省时间。

## 5. 方案 B：公司统一机器人 + 多用户独立 OAuth

### 5.1 适用范围

适用于公司内多人正式使用。公司只维护一个飞书机器人和一套服务，但每名员工以自己的飞书身份授权。消息读取范围由飞书用户权限和应用 scope 共同决定。

### 5.2 方案架构

```text
员工 A ─┐
员工 B ─┼─> 同一个飞书机器人 ─> 本地或云端应用服务
员工 C ─┘                           │
                                    ├─ open_id 身份解析
                                    ├─ OAuth state 一次性校验
                                    ├─ 每用户加密 Token Vault
                                    ├─ 用户态聊天读取
                                    ├─ 共用摘要模块
                                    └─ 仅回复原请求者
```

这里的“多人共用”仅指共用入口、代码和运维。用户令牌、消息权限、摘要结果和任务草稿必须逐人隔离。

### 5.3 明确实施内容

| 模块 | 实施内容 | 交付物 |
| --- | --- | --- |
| HTTPS 入口 | 提供稳定公网 HTTPS OAuth 回调，可使用正式域名和反向代理/隧道完成试点 | 可访问的回调 URL |
| OAuth | 按 `open_id` 创建一次性 state、交换 code、支持 token 刷新和撤销后的重新授权 | OAuth 服务与回调页 |
| Token Vault | AES-256-GCM 加密、按 `open_id` 隔离、限制文件权限或迁移到密钥服务 | 加密令牌存储 |
| 用户态读取 | 使用每名用户自己的 access token 调用搜索和批量读取 API | OAuth Provider |
| 权限控制 | 请求者、token owner、摘要接收者三者必须为同一 `open_id` | 强制身份绑定检查 |
| 授权体验 | 未授权时发送授权链接；成功后提示重新发送请求；支持取消授权说明 | 用户引导文案 |
| 审计 | 记录授权、读取请求和结果状态，不记录消息正文和令牌 | 最小化审计事件 |
| 运维 | 健康检查、错误率、延迟、token 刷新失败告警、备份恢复 | 运行手册和监控 |
| 灰度 | 先允许名单，再分部门扩展，最后全员开放 | 分阶段发布配置 |
| 合规 | 明确用途、保留期限、管理员边界和员工退出处理 | 隐私与权限说明 |

### 5.4 实施步骤

#### B1. 权限与合规评审

1. 列出实际需要的用户身份 scope，只申请消息搜索、读取和离线刷新所需最小集合。
2. 明确数据流、处理目的、数据保留和删除策略。
3. 明确管理员不能直接查看员工摘要或原始聊天。
4. 明确员工离职、撤销授权和设备丢失时的处理方式。
5. 由公司应用管理员和信息安全负责人确认。

验证：权限清单、数据流图、撤销流程和责任人均有书面记录；未完成评审不得全员开放。

#### B2. 建立稳定 HTTPS OAuth 入口

1. 试点可使用受控 HTTPS Tunnel；正式环境优先使用公司域名和受管服务。
2. 在飞书开发者后台配置完全一致的 redirect URI。
3. 回调只允许 HTTPS，不接受任意重定向目标。
4. 加入健康检查、访问日志脱敏、速率限制和进程守护。

验证：公网回调可用；错误 state 返回固定失败页；授权 code 不进入日志；服务重启后域名保持不变。

#### B3. 完善逐用户 OAuth 生命周期

1. state 绑定发起授权的 `open_id`，设置短期有效期并保证只消费一次。
2. code 交换结果只写入对应用户的 Token Vault。
3. access token 到期前刷新；刷新失败时删除本地失效令牌并要求重新授权。
4. 提供本地删除单个用户令牌的运维命令或受控接口。
5. 禁止把 token、code 和底层 SDK 请求写入日志。

验证：跨用户 state、过期 state、重放 state、篡改 state 全部失败；A 用户的 token 永远不能用于 B 用户请求。

#### B4. 强制端到端身份绑定

1. 从飞书事件提取请求者 `open_id`。
2. 用同一 `open_id` 查 Token Vault。
3. 用该 token 读取消息。
4. 摘要和任务草稿只能回复、归属该 `open_id`。
5. Leader 汇总、群聊和管理员接口不得复用私人摘要数据。

验证：自动化测试覆盖请求者、token owner、摘要接收者任意两者不一致的情况，全部拒绝且不读取消息。

#### B5. 完善读取与摘要可靠性

1. 保持搜索全分页、消息分批读取、文本过滤、去重和排序。
2. 达到分页上限时标记 `incomplete`，不得把不完整结果伪装成完整摘要。
3. 设置单次最大日期跨度和消息数量保护；超过限制时引导用户缩小范围。
4. 对长消息分块摘要后再合并，并保持固定 JSON 结构。
5. MiniMax 失败时不落原文，返回可重试提示。

建议第一版最大范围为 31 天；如真实数据表明 31 天仍过大，再按消息数量进一步收紧。

验证：分页、批量上限、空消息、非文本、超长范围和模型失败均有自动化测试与明确用户反馈。

#### B6. 灰度发布

1. 阶段 1：3～5 名跨职能员工试点 2 周。
2. 阶段 2：一个部门试用 2～4 周。
3. 阶段 3：完成安全复核后逐步全员开放。
4. 每阶段复盘成功率、准确率、使用频率、授权失败率和用户投诉。
5. 任一高严重度越权或泄露事件立即关闭聊天总结开关，不影响客服和任务功能。

验证：功能开关能独立关闭聊天总结；关闭后 OAuth 服务、Token Vault 和聊天读取均不启动，其他功能正常。

#### B7. 运维与交接

1. 建立部署、升级、回滚、密钥轮换、令牌清理和故障排查手册。
2. 配置进程守护和日志轮转。
3. 监控 OAuth 成功率、读取成功率、P95 延迟、刷新失败率和模型失败率。
4. 定期抽查日志，确认不含消息正文与令牌。
5. 指定应用管理员、服务维护人和安全事件联系人。

验证：非开发人员按手册能完成重启、关闭聊天总结、清理单个用户令牌和回滚上一版本。

### 5.5 方案 B 验收标准

| 类别 | 验收项 | 明确标准 |
| --- | --- | --- |
| 功能 | 多用户独立使用 | 至少 5 名试点用户可分别授权、读取自己的可见消息并收到摘要 |
| 隔离 | 跨用户访问 | 跨用户 token、state、摘要接收和任务归属测试 100% 被拒绝 |
| 权限 | 飞书权限继承 | 用户无权访问的会话，助手同样无法读取；不得使用管理员或公共账号绕过 |
| OAuth | state 安全 | state 有效期、一次性消费、用户绑定和防重放测试全部通过 |
| OAuth | 刷新与撤销 | token 可自动刷新；撤销或刷新失败后停止读取并要求重新授权 |
| 隐私 | 原文与凭证 | 原始正文、access token、refresh token、code 不进入持久化日志、Base 和他人消息 |
| 功能 | 分页完整性 | 正常范围读取所有页面；达到保护上限时明确标记不完整 |
| 质量 | 事实准确率 | 抽样摘要事实正确率不低于 95%，未确认建议不得写为已确认决策 |
| 质量 | 用户可用率 | 至少 70% 的摘要被评价为可直接使用或仅需轻微编辑 |
| 性能 | 响应时间 | 95% 的 7 天范围请求在 60 秒内完成或返回明确状态 |
| 稳定性 | 请求成功率 | 排除用户主动撤销授权后，试点期端到端成功率不低于 95% |
| 可恢复 | 故障隔离 | 任一用户授权失败不影响其他用户；关闭总结不影响客服、任务和提醒 |
| 审计 | 可追踪率 | 100% 读取请求有请求者、范围、数量、耗时和状态记录，但无正文 |
| 运维 | 回滚 | 15 分钟内可关闭聊天总结或回滚上一稳定版本 |
| 回归 | 自动化测试 | 全量测试通过，并覆盖 OAuth 防重放、跨用户隔离、刷新失败和功能开关 |

## 6. 两套方案对比

| 维度 | 方案 A：单用户 CLI | 方案 B：多用户 OAuth |
| --- | --- | --- |
| 目标 | 快速验证业务价值 | 公司正式推广 |
| 使用人数 | 1 名固定试点用户 | 多名员工 |
| 机器人数量 | 1 | 1 |
| 用户身份 | 本机 CLI 当前登录用户 | 每名员工自己的 OAuth 身份 |
| HTTPS 回调 | 不需要 | 需要稳定公网 HTTPS |
| Token 管理 | 由 `lark-cli` 管理 | 应用按 `open_id` 加密管理 |
| 权限隔离 | 允许名单 + 单 CLI 身份 | 飞书权限 + 每用户 Token Vault |
| 部署复杂度 | 低 | 中高 |
| 运维成本 | 低，但依赖固定机器 | 较高，可标准化运维 |
| 审计能力 | 基础 | 完整 |
| 公司合规适配 | 仅限受控试点 | 可进入正式评审 |
| 横向扩展 | 不适合 | 适合 |
| 主要风险 | CLI 登录态被误用于其他用户 | OAuth、密钥和跨用户隔离实现错误 |

## 7. 从方案 A 升级到方案 B 的复用与替换

### 7.1 原样复用

- 飞书机器人消息入口。
- 时间范围解析和日期校验。
- 统一消息结构。
- 文本过滤、去重、排序和分页完整性标志。
- MiniMax 摘要和分块合并。
- 任务草稿与人工确认。
- 私聊回复、错误提示和大部分测试。

### 7.2 需要替换

- `LarkCliChatHistoryProvider` 替换为 `OAuthChatHistoryProvider`。
- 唯一用户允许名单替换为逐用户授权状态。
- CLI 登录态运维替换为 OAuth state、Token Vault 和刷新机制。
- 本机单进程运行增强为稳定 HTTPS、监控、灰度和回滚体系。

### 7.3 必须删除或禁用

- 多人模式下不得保留“所有请求共用本机 CLI 用户”的回退路径。
- 不得在 OAuth 失败时静默使用公共 CLI 身份读取。
- 不得把单用户允许名单误当成公司级权限系统。

## 8. 推荐开发顺序

| 顺序 | 工作项 | 完成标志 |
| --- | --- | --- |
| 1 | 定义 `ChatHistoryProvider` 契约 | OAuth 现有测试通过契约测试 |
| 2 | 新增 CLI Provider 失败测试 | 未登录、恶意输入、超时和错误输出可稳定复现 |
| 3 | 实现 CLI Provider | 最小实现使测试通过 |
| 4 | 增加唯一用户门禁 | 非允许用户读取调用数为 0 |
| 5 | 条件化配置与组装 | CLI 模式不启动 OAuth；OAuth 模式不调用 CLI |
| 6 | 单用户真实联调 | 已知消息范围能得到可核验摘要 |
| 7 | 完成 1～2 周试点复盘 | 达到方案 A 晋级门槛 |
| 8 | 权限与合规评审 | scope、数据流、撤销和责任人确认 |
| 9 | 部署稳定 HTTPS OAuth | 回调、健康检查和脱敏日志通过验收 |
| 10 | 完善多用户隔离测试 | 跨用户场景 100% 拒绝 |
| 11 | 3～5 人灰度 | 达到方案 B 试点标准 |
| 12 | 部门级与全员推广 | 每阶段有复盘和继续/停止决策 |

## 9. 上线决策门

### 9.1 方案 A 可以启动的条件

- 唯一试点用户和 `open_id` 已确认。
- `lark-cli` user 身份授权成功。
- CLI 调用不经过 shell 拼接。
- 非允许用户无法触发读取。
- 原文不落盘测试通过。
- 全量自动化测试通过。

### 9.2 方案 A 可以升级到方案 B 的条件

- 连续试点至少 1 周。
- 每周至少有 3 次真实主动使用。
- 请求成功率不低于 90%。
- 摘要事实准确率不低于 95%。
- 用户确认平均节省至少 30% 的人工整理时间。
- 无越权读取、正文泄露或错误接收者事件。

### 9.3 方案 B 可以扩大推广的条件

- 公司权限与合规评审通过。
- 逐用户 OAuth 和跨用户隔离测试全部通过。
- 3～5 人灰度至少运行 2 周。
- 端到端成功率不低于 95%。
- P95 响应时间不高于 60 秒。
- 有明确运维负责人、关闭开关和 15 分钟内回滚能力。

## 10. 最终结论

公司最终形态应是“一个统一机器人入口 + 每人独立身份与权限”，而不是每人部署一个机器人，也不是多人共用一个员工账号。

实施上先做方案 A，可以用最低成本证明需求是否真实存在；架构上从第一天就隔离消息读取 Provider，确保试点成功后只替换身份和令牌来源，不重写时间解析、摘要、任务草稿和用户入口。只有方案 A 达到明确的使用频率、成功率、准确率和节省时间门槛，才投入方案 B 的 HTTPS、OAuth、审计与公司级运维建设。
