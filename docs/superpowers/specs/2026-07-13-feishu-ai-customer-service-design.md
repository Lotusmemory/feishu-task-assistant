# 飞书 AI 智能客服演示版设计

## 目标

实现一个本地运行的飞书 AI 机器人，验证以下最小闭环：

1. 用户在飞书中私聊机器人，或在群聊中 `@机器人` 并发送文本。
2. 本地 Node.js 服务通过飞书长连接接收消息。
3. 服务调用 MiniMax M3。
4. 机器人在飞书中回复原消息。

本阶段是链路演示，不建设完整客服系统。

## 成功标准

- 私聊机器人的非空文本能得到 MiniMax M3 回答。
- 群聊中未 `@机器人` 时保持沉默。
- 群聊中 `@机器人` 时移除 mention，并回答用户问题。
- 同一飞书事件在单次进程生命周期内不会被重复回答。
- MiniMax 请求失败时，用户收到不泄露内部信息的简短提示。
- 自动化测试覆盖核心消息判断与模型调用错误路径。
- README 能指导用户完成配置和本地启动。

## 技术方案

采用 Node.js、飞书官方 Node.js SDK和 MiniMax HTTP API。

飞书应用使用长连接接收 `im.message.receive_v1` 事件，不需要公网域名、HTTPS 回调或内网穿透。模型调用使用 MiniMax 官方 HTTPS 接口，模型固定为 `MiniMax-M3`。

## 架构与职责

### 配置加载

从环境变量读取：

- `FEISHU_APP_ID`
- `FEISHU_APP_SECRET`
- `MINIMAX_API_KEY`
- `MINIMAX_BASE_URL`，提供 MiniMax 官方地址作为默认值
- `MINIMAX_MODEL`，默认 `MiniMax-M3`

程序启动时校验必需配置。真实凭证仅保存在本地 `.env`；仓库只提供 `.env.example`，并通过 `.gitignore` 排除 `.env`。

### 飞书消息处理器

消息处理器接收飞书事件并执行以下流程：

1. 按 `message_id` 检查内存去重集合，重复事件直接忽略。
2. 忽略机器人自身消息、非文本消息和空文本。
3. 私聊消息直接进入模型调用。
4. 群聊消息仅在明确 `@机器人` 时处理，并在调用模型前移除 mention。
5. 获得模型最终文本后，回复原飞书消息。

去重数据只保存在内存中，进程重启后可以丢失。

### MiniMax 客户端

客户端接收单条用户文本，使用固定的客服 system prompt 调用 `MiniMax-M3`。每次请求相互独立，不携带历史会话。

客户端只返回最终回答文本，不向飞书发送模型推理内容。请求设置有限超时，避免模型接口异常时永久占用处理流程。

## 用户可见行为

- 私聊：非空文本触发回答。
- 群聊：只有 `@机器人` 的文本触发回答。
- 回复：使用回复原消息的方式，明确答案对应的问题。
- 图片、文件、语音、卡片和空消息：静默忽略。
- 模型不可用：回复“暂时无法回答，请稍后重试”。

## 日志与错误处理

- 启动配置缺失时立即退出，并指出缺少的环境变量名。
- MiniMax 超时、非成功状态码、无有效回答或飞书回复失败时，记录结构化错误到本地控制台。
- 日志不得打印飞书应用密钥、MiniMax API Key 或完整鉴权请求头。
- 用户侧错误信息不包含模型原始响应、堆栈或凭证。

## 测试设计

### 单元测试

- 私聊非空文本会触发处理。
- 群聊未 mention 机器人时不处理。
- 群聊 mention 机器人时正确移除 mention。
- 空文本和非文本消息被忽略。
- 相同 `message_id` 的事件只处理一次。
- MiniMax 成功响应能提取最终回答。
- MiniMax 超时、错误状态和空响应会转换为统一错误。

### 人工验收

1. 启动本地服务并确认飞书长连接成功。
2. 私聊机器人发送文本，确认机器人回复。
3. 群聊发送普通文本，确认机器人不回复。
4. 群聊 `@机器人` 提问，确认机器人回复原消息。
5. 临时配置无效 MiniMax Key，确认用户只看到通用错误提示，控制台不泄露密钥。

## 明确不做

- 多轮上下文和持久化聊天记录
- 企业知识库或 RAG
- 图片、音频、文件理解
- 转人工、工单、客服排队和服务质量统计
- 管理后台、用户权限和运营配置
- 云端部署与高可用

这些能力只有在最小闭环验收通过后，才按实际客服目标单独设计。
